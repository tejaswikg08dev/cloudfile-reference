Data Model & Ownership

Three tables. Who owns each, and who reads or writes it.

👤

users

owned by auth

id · email (uniq) hashed_password full_name · is_active created_at
📄

files

owned by files · read by search · updated by processor

id · owner_id (idx) filename · content_type size_bytes · s3_key (uniq) status · thumbnail_key created_at
✉️

notifications

owned by notification (separate repo / own DB)

id · recipient (idx) subject · message channel · status created_at

Who touches the files table?

ServiceAccessWhy
filesread + writeowns the lifecycle (create, confirm, delete)
searchread onlya read model for filtering/pagination
processor (Lambda)updatesets status=processed + thumbnail_key
Honest trade-off: files and search sharing one table isn't pure microservices isolation. It's a pragmatic read model (CQRS-lite). The upgrade path is an event bus (SNS/SQS) projecting into a search-owned datastore — call this out in interviews, it shows maturity.
status moves through three values: pending (row created) → ready (client confirmed) → processed (Lambda finished).
